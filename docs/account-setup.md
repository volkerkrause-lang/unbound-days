# Group A development setup

Nothing here changes the existing production application. Use an isolated development Supabase Free project and a local/staging frontend. No paid upgrade required for development.

1. In Supabase create a **development** project, choosing the UK/London region if available. Keep email confirmations enabled. Apply `supabase/migrations/202610140001_accounts.sql` using its SQL editor (or Supabase CLI migrations). Never apply to production without separate approval.
2. In `account-config.js`, set the development project URL and **publishable** key only. Never use a secret/service-role key. This file is served publicly. Do not commit private SMTP/Google/service credentials.
3. In Auth URL Configuration set Site URL to the staging origin; allow the exact local/staging root callback URLs (local `http://localhost:4173/`). Avoid broad wildcard release redirects. PKCE email confirmation/reset normally requires the initiating browser/device.
4. Configure custom SMTP for public test addresses: sender domain DNS verification, SMTP host/port/user/password, From name/address. Default Supabase SMTP only supports project-team addresses and a small testing rate limit. Keep SMTP credentials in Supabase settings. Enable password minimum 12 characters and appropriate Auth rate limits. Before public testing enable Supabase Turnstile CAPTCHA, set its secret in Auth and public site key in `account-config.js`; allow only the staging/release hostnames.
5. For Google login, create a Google Cloud Web OAuth client. Put the client ID/secret in the **Supabase Google provider**, with Supabase's displayed `/auth/v1/callback` as the authorized Google redirect. Add test users/consent configuration. This is login only; no Calendar/Tasks/Drive scopes are requested here.
6. Deploy the deletion function to development with Supabase CLI: `supabase functions deploy delete-account --project-ref YOUR_DEV_REF`. Set function secret `APP_ORIGINS` to exact comma-separated local/staging origins, no trailing slash. Supabase supplies its URL/anon/service-role environment keys. Never put service-role keys in frontend code. The function verifies the user token and rechecks the password through Auth before deleting that user's account. Deletion cascades to live notebook/profile/import records; hosted backup/log retention must still be addressed before release. Separate Drive/Dropbox copies and guest notebooks are not deleted. Google-only accounts must first set a password through reset email.
7. Sign up and verify YOUR account, copy its UUID from Supabase Auth Users, independently confirm it is yours, then run privileged SQL: `update public.profiles set role='admin' where id='YOUR_VERIFIED_UUID';`. User-provided metadata/email never grants admin. Admin feature access does not permit reading anyone else's planner.
8. Run `npm ci`, `npm run check`, `npm test`, `npm start`. `npm start` builds `_site` and serves it locally. No production services activated. For proposed Cloudflare Pages staging use build command `npm run build`, output `_site`; `_headers` prepares CSP/security headers. Authenticated requests go to Supabase, not static host. Keep production publishing separate.

## Migration / verification

Before any hostname change, open the OLD site and export its complete JSON notebook; the new origin cannot read its local stores. Retain the old notebook and downloaded file. Log in on development, use My Account → Import legacy notebook (same origin) or Import legacy export file. Import downloads a recovery export, validates JSON roundtrip/schema, fingerprints it, and inserts transactionally only into an account without a cloud notebook. Repeated migration is rejected. Current unsynced account writing is snapshotted before replacement. No automatic claim of the guest notebook.

Local notebook and IndexedDB copies are UUID-scoped for signed-in accounts; guest key/recovery remain unchanged. Browser cache is not encrypted against someone with physical/browser-profile access. On logout, the notebook is locked and reloaded into the guest scope; account drafts remain for retry. On shared devices export/sync, then clear site data when finished. Other devices load live database data, not Drive backups. Same-field conflicts require explicit choices in My Account; concurrent changes use revision checks. Network failures retain local data and retry on reconnect/periodic active checks. Offline Google edits remain blocked as before.

Run the prepared browser smoke using `npx playwright install chromium`, start local app, then `npm run test:browser`. The smoke expects blank account configuration and uses a fresh disposable browser context. For configured staging also manually verify signup/confirmation, Google login, reset/password change, logout/switching, two-device conflicts and offline/reload, then deletion of a disposable account. Record these results before declaring Group A complete. Database tests run real PostgreSQL/WASM RLS/CAS behavior (PGlite), not a live hosted Supabase service.

Group B and C have not started. Calendar/Drive remain legacy adapters; authenticated notebooks disable Drive journal merging so the database is authoritative. Existing optional provider backups are still available but protected backend Google authorization/account-binding waits for Group B. Do not release publicly until all groups and release gates are verified.
